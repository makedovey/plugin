# The tools this plugin's skills name

Generated by api/scripts/build_plugin_skill.py from the tools' own descriptions (api/core, the registry the MCP server lists). The full list is what your host shows for the `klayson` server.

## add_page

Add a page to a brand's system, or a subpage under a page (parent; one level deep). For anything the standard pages do not hold: "Social profile banners", "Packaging", "Typeface hierarchy". For people who can edit the brand; people who can only view use suggest_change. How to structure a page (you do the structuring; Klayson stores it as sent): title, a short name. use_when, one line saying when an agent should fetch the page ("Making a banner for a social profile"). blocks, a list, each {kind, type, name, data, visual, text}. kind value: one token in data, by type: color {hex, role}, type_style {family, weight, size, line_height, tracking}, font {family, weights}, spacing, radius, size and breakpoint {value or width and height, unit}, shadow {box_shadow}, motion {duration_ms, easing}, asset {url}, component {css or html}, section, recipe {sections}, text. Use the brand's own token names from get_page (its colors, its fonts), never a new name for the same value. kind rule: text holds the rule in the source's own words, never rewritten. kind example: a real example, a picture as visual {kind: image, url} or code in data. visual is what draws it: swatch {hex}, specimen {family, weight, size}, render {css or html}, image {url}, logo {url}. Leave out what the source does not state: never invent a value. Answers the page's path. This is a page of the brand's system, not a canvas.

## capture_codebase

Send the design values you read from this repo, so every agent reads the brand as the code has it. You are the reader: Klayson parses nothing. Read the design tokens (colors with their roles, type styles, spacing, radius, shadows, breakpoints), the fonts, the logo files (send each through create_upload_link, then name it in a block), and the components with their variants and a short code snippet each. Send them as pages in get_page's shape, each block with source_ref {file, line}, plus repo {name, framework, files: the paths you read}. Never send secrets, env files or application code. Tell the person what you are sending first. Stored as source codebase: where the site says the same thing the codebase wins, an owner's edit still wins over both, and sending again replaces the last capture. For people who can edit the brand.

## check_against_brand

Check a picture or a canvas frame against a brand's own pieces (its running ads and posts): the palette, the ground, the case, where the logo sits, how large the product is, whether a button is drawn. Answers a score (0 to 1) and notes worst first, each with what was measured, what the brand does and the fix, and `against`: which brand or read it was checked against. Give a design_id (a frame of this workspace), an asset_id, or a public image_url. By default the check is against the workspace's own brand (`brand` picks one of several); read_id checks against a site read with extract_brand instead (depth full, so it has the brand's pieces). Use it to check a finished picture before it is shown. 1 API credit with an API key or on /mcp/brand. The answer says credits_remaining.

## check_design

Render a page you built against a design context pack and list what is wrong, each with its fix: console errors, files that did not load, the brand's fonts not on screen, overflow at 390px, clipped text, low contrast, generic-AI tells, the logo or pictures redrawn instead of used, a page that did not style. Give html (your index.html; the pack's paths fonts/… and brand/… load from the pack, anything else needs a full https address) or the public url of the page. Answers job_id: get_job(job_id, wait true) gives problems, the page's outline and screenshots at 1440 and 390 to compare with the pack's reference/. Fix, then check again. 1 API credit with an API key or on /mcp/brand.

## create_brand

Add a brand to the workspace (an agency's client, a second line). One of: url, the brand's website, read in full (answers the brand and a job_id; get_job with wait true until it is done, then read the brand with brand set to its id); read_id, a full read from extract_brand saved as the brand without reading again; guide_asset_id or guide_url, the brand's own brand guide as a PDF, Word, PowerPoint or Google Docs/Slides guide (a file goes through create_upload_link kind=file; a Google link is passed as it is), read into the brand (the name comes from the guide unless given; answers a job_id for get_job); or name alone, a brand by hand for a business with no website. A site the workspace already has answers that brand (existing: true), never a copy.

## create_upload_link

Get a link that puts images straight into this workspace, for a file attached in chat or on the person's computer (a chat attachment cannot be passed as an argument). If you can run a shell or code and the file is on disk (a path you were given, an upload folder), send it yourself: run upload_command with the file's path; the answer is the asset. Otherwise give the person the upload_url to click and drop their images on. The link works for an hour, as many times as needed, and only adds images to this workspace. kind defaults to product (screen for an app or website screenshot). kind file takes a document instead: the brand's own brand guide as a PDF, Word (.docx), PowerPoint (.pptx), text or markdown file, up to 50 MB; its asset_id is what import_brand_guide takes. A Google Docs or Google Slides guide needs no link: pass its share link as url to import_brand_guide. kind library takes what the brand's library keeps: a picture, a GIF, an MP4 or WebM video up to 50 MB, or a Lottie JSON.

## decide_suggestion

Approve or reject a suggested change to a brand's system. Approving applies it as the suggester's edit; rejecting changes nothing. For people who can edit the brand; where edits need the owner's approval, the workspace's owner only. Decide only when the person told you to.

## extract_brand

Read a brand from its website and keep its materials: every stylesheet and the rendered page, the webfont files it serves, every logo candidate, its largest pictures and a screenshot, plus the measured description (colors with roles and shares, type per role with the real family and its files, buttons and cards as CSS, surfaces, sections). Any public site, the person's own brand or another; the files come back behind links that expire in seven days. depth: full adds everything else Klayson reads: what the brand is, its audience and voice, products and prices (the store's whole catalogue from its feed, up to 500; photos and the cutout are kept for the first 8), offers and proof, its design system, its photographs, its own running ads and how it composes them. Answers read_id at once. Poll get_brand_extract(read_id): the measured read lands first, in 15 to 35 seconds on the sites we timed, each richer section as it finishes, with a status per section. A recent read of the same address is answered at once; fresh: true forces a new one. 1 API credit a site, 2 with depth full (a read that fails gives them back; asking again for an address this workspace already read costs nothing); the answer says credits_remaining.

## extract_design_context

Read a site's UI into a design context pack, so you can build pages that look like the brand: DESIGN.md (measured colors and roles, page tone, the logo, fonts that load, type roles with letter-spacing, shadows, the real nav, buttons, card and input CSS, the section outline) plus files (reference screenshots, the logo, font files, the brand's own pictures, brand/nav.html). Reads the home page and up to two inner pages from its nav (page_url names the one to read). Leave url out for this workspace's own brand (free; its font files included). Another site costs 2 API credits and its fonts come as files only when open-licensed, else as a named open substitute. Answers pack_id and job_id: get_job(job_id, wait true), then get_design_context(pack_id).

## get_api_credits

The workspace's Brand API credits: the balance and the last 50 changes (each with what it was for: free, topup, extract_plain, extract_full, check, refund). extract_brand costs 1 API credit a site (2 with depth full); check_against_brand costs 1 when called with an API key or on /mcp/brand; reading kept results costs nothing. Every workspace starts with 25 free API credits; they never expire.

## get_brand

The brand, as an agent should read it first: the Overview page in full (what the brand is, its personality, its rules) and the list of every page and subpage with its use_when, the line that says when to fetch it. Call this before you make anything for a brand, then get_page for the pages the job needs. Never a dump: one page at a time. The pages are Brand (overview, logo, colors, typography, voice, imagery, products), Design system (layout, components, sections, pages, motion), Mediums (web, app, ads, social, slides, email, print) and the team's own. Works for every brand of the workspace you may see (brand picks one).

## get_brand_extract

One brand read as Brand Extract v1, as far as it has landed: `status` (reading, then complete, partial, blocked or failed, with `reason` and `next_step` when it is not complete) and `sections` (each pending, done, skipped or failed) say what is in; ask again while it is reading. A blocked or failed read was not charged. Brand and facts (with depth full, or the workspace's own site; facts.products is the store's whole catalogue, each with its name, price, link, first picture and variants, and the first 8 also with their kept photos, description and cutout), identity (colors with role, usage and share; type per role with the real family, its font files, licensing and specs; buttons and cards as CSS; surfaces; logos; pictures), the design system, the site's photographs, the brand's own pieces and how it composes them, the page's sections, the kept HTML, CSS and screenshot. Every field says its source (computed, css, pixels, site, ad_library, instagram, model) and a confidence; file links expire in seven days. get_brand_materials lists the read ids.

## get_brand_materials

The brand materials this workspace has read (extract_brand, or the brand read with the materials step on): the measured description and, for one read_id, every kept file as a link that expires in seven days (fonts, logos, pictures, stylesheets, the page, a screenshot).

## get_design_context

A design context pack: DESIGN.md (format md, the default) or its structured JSON (format json), and every file as a signed link (7 days). How to use it: download each file into your project at its path (reference/, fonts/, brand/); read DESIGN.md and open the reference screenshots, matching their composition, tone, nav and buttons; use brand/logo.* and brand/visual-*.jpg exactly as they are, never redrawn; load fonts with DESIGN.md's @font-face rules; start the nav from brand/nav.html; then call check_design and fix what it lists. With no pack_id it answers the brand's own pack, building it the first time (poll get_job). page_type (home, feature, about, ...) keeps one page's screenshots and outline.

## get_job

Status of a background job, such as a brand being read by create_brand: queued, running, done or failed. done carries output, failed carries error. wait true answers once the job is done or failed (up to about 40 seconds; call again with wait true while it still runs), so no polling.

## get_library

The brand's library: the work its team approved and the references it keeps, newest first, by medium (web, app, ads, social, slides, email or print), so work made for a medium can match what was approved there: its layout, its density, its tone. The brand's own running ads and social posts are in it as approved. Filter by status (approved or reference), medium and kind (image, video, motion, code, page, link). Each card has its title, kind, medium, status, a picture (thumb_url), its address or the start of its code, and a note on why it is good. item_id answers one item in full, its whole code included. A reference is something the team likes that is not its own: take the idea, never copy it.

## get_me

Who am I: the person, the workspace and its plan, the brand (and brands, when it holds several) and the Brand API credits left. Read-only: call it to verify the connection.

## get_page

One page of a brand's system in full: its blocks in order, each a value (tokens in data), a rule (in words, in text) or an example, with its source (measured, guide, codebase, inferred or edited), what draws it (visual) and the files as links (7 days). A section's visual is its own picture, or the page's screenshot with crop {y0, y1, page_width, page_height} in that picture's pixels: only that part is the section. A learned rule's source_ref.examples are the pieces it was learned from. unknown lists what has not been read: do not invent it. A block with latest_read was edited by an owner, or sent from the codebase, and the site now says something else: the edit, then the codebase, wins. Subpages are listed; get_page each one you need. page is a key from get_brand (colors) or a subpage's path (typography/hierarchy).

## import_brand_guide

Read the brand's own brand guide into its brand guide: a PDF, Word, PowerPoint or Google Docs/Slides guide (or a text or markdown file). Fills empty fields only, unless replace is true; never a field a person or an agent edited. About a minute.

## list_suggestions

The suggested changes to a brand's system, newest first: each with its page, the change, who suggested it and its status (open, approved, rejected). People who can edit the brand see every one; people who can only view see their own. decide_suggestion approves or rejects one.

## save_to_library

Save something to the brand's library, as approved work or as a reference, so every agent sees it before making something for that medium. Save only after your person approves something you made, or shares something they like. Ask once ("Save this to Klayson as approved?") and save on a yes. Never save on your own reading of anyone's words. Give exactly one of: asset_id, a file uploaded through create_upload_link with kind library (a picture, a GIF, an MP4 or WebM video, or a Lottie JSON); url, a web page (Klayson takes a picture of it for its card) or a picture or video at an address; or code with code_lang (html, jsx, tsx or css: Klayson keeps the code and draws a picture of it). status is approved (the default) or reference (something they like that is not their own). medium is where it is used: web, app, ads, social, slides, email or print. title is a short name, note one line on why it is good. A picture that has to be made comes from a job: get_job with its id and wait true when you need it.

## suggest_change

Propose a change to a brand's system for someone who can edit it to approve. For anyone who can see the brand; the way people who can only view change it. Either page with what update_page takes (title, use_when, blocks, remove_blocks), or new_page with what add_page takes ({title, use_when, parent, blocks}). note says why, in a line. Nothing changes until it is approved. How to structure a page (you do the structuring; Klayson stores it as sent): title, a short name. use_when, one line saying when an agent should fetch the page ("Making a banner for a social profile"). blocks, a list, each {kind, type, name, data, visual, text}. kind value: one token in data, by type: color {hex, role}, type_style {family, weight, size, line_height, tracking}, font {family, weights}, spacing, radius, size and breakpoint {value or width and height, unit}, shadow {box_shadow}, motion {duration_ms, easing}, asset {url}, component {css or html}, section, recipe {sections}, text. Use the brand's own token names from get_page (its colors, its fonts), never a new name for the same value. kind rule: text holds the rule in the source's own words, never rewritten. kind example: a real example, a picture as visual {kind: image, url} or code in data. visual is what draws it: swatch {hex}, specimen {family, weight, size}, render {css or html}, image {url}, logo {url}. Leave out what the source does not state: never invent a value.

## update_page

Change a page of a brand's system: its title, its use_when, its place (position), hidden or not, and its blocks. blocks adds blocks and replaces the ones of the same type and name; remove_blocks takes blocks off by name (kept, never deleted). What you write is an edit: it wins over anything read from the site or a guide, and a later read never overwrites it (the read is kept beside it as latest_read). For people who can edit the brand; people who can only view use suggest_change. Only change what the person asked for. rev (from get_page) refuses the write if the page changed since. How to structure a page (you do the structuring; Klayson stores it as sent): title, a short name. use_when, one line saying when an agent should fetch the page ("Making a banner for a social profile"). blocks, a list, each {kind, type, name, data, visual, text}. kind value: one token in data, by type: color {hex, role}, type_style {family, weight, size, line_height, tracking}, font {family, weights}, spacing, radius, size and breakpoint {value or width and height, unit}, shadow {box_shadow}, motion {duration_ms, easing}, asset {url}, component {css or html}, section, recipe {sections}, text.
